# Sprout Hollow Valley surface completeness inventory

## Inventory rules

This is the hand-written completeness inventory for the Sprout Hollow Valley
desktop shell and responsive Pages site. Both surfaces must implement every required
row independently. Shared source may reduce duplication, but evidence from one surface
does not complete the other.

This inventory is intentionally honest about the current foundation:

- **Foundation** means a relevant inherited implementation path exists, but the Valley
  contract, focused tests, packaged interaction record, capture, or all four remain
  incomplete. Foundation never means release-complete.
- **Planned** means the required implementation is not yet adequate or does not yet exist.
- **Not applicable** is used only for the three browser-extension download states because
  Sprout Hollow Valley does not deliver a browser extension. A normal installer link is a
  different browser-managed flow. If an extension is added, all three rows immediately
  become required.

No row in this document is marked complete. Existing `docs/COMPLIANCE.md` describes
historical Sprout Hollow source and checks; it does not prove the Valley product, Material
3 migration, current packaged shell, responsive site, 3D world, content totals, or real
captures.

## Evidence target conventions

Every row below has a stable ID. Its exact evidence targets are derived from that ID:

| Surface | Built interaction record target | Real capture target |
| --- | --- | --- |
| Desktop shell | `evidence/valley-shell/interactions/<ID>.json` | `evidence/valley-shell/captures/<ID>.png` plus a matching metadata record |
| Pages site | `evidence/valley-site/interactions/<ID>.json` | `evidence/valley-site/captures/<ID>.png` plus a matching metadata record |

The tables state the interaction and capture scenario that each exact target must contain.
These paths are targets, not claims that evidence exists. An interaction record must name
the built commit, package or deployment identity, steps, assertions, accessibility state,
and result. A capture record must name the same build, route, viewport, language, theme,
and feature state and must hash the referenced image. Source previews, injected state,
mocked IPC, reused images, or captures from another row do not satisfy a target.

Desktop localization code **S-L10N** means `src/shell/core/strings.ts` through
`src/shell/core/i18n.ts`: English, playful Hong Kong Cantonese, compact bilingual output,
independent English and Cantonese funny levels 1–5, School-mode behavior, and emoji-off
alternatives. Existing keys are only a foundation; each row still needs exact feature keys.

Site localization code **W-L10N** means the planned bundled `site/i18n.ts` and
`site/strings.ts` with the same three language modes, two funny-level controls,
School-mode behavior, and emoji-off alternatives. No network translation is allowed.

## Responsive Pages site inventory

### Exact surface boundary

The Pages site is never a playable game surface. It provides only landing, marketing,
documentation, download, settings, accessibility, evidence, changelog, and release
information. It does not embed, host, stream, delegate, or run the 3D game, game controls,
farm simulation, NPC simulation, or save simulation. The playable product exists only in
the packaged desktop Electron application.

Gameplay controls and simulation therefore have explicit Not applicable rows below for
this exact surface-boundary reason. That status does not exempt any universal site feature:
language, settings, navigation, Material 3, utilities, accessibility, local tools, locks,
and evidence presentation remain independently required on the site.

The site may later show genuine screenshots produced from an identified packaged desktop
build and verified links to its releases. This documentation run produced no capture proof,
and none of the capture targets below claim otherwise.

The site must work from approximately 320 pixels wide through large desktop viewports,
with no sideways body scroll, locally bundled assets, no analytics, and per-visitor state
stored locally. Where the desktop contract names an OS credential vault or application-data
folder, the site uses a clearly disclosed browser-storage equivalent. That equivalent is
not a security claim and must never send visitor data to a server.

## Executable negative-regression design

The future executable guard must use a fixed, hand-written `REQUIRED_FEATURE_IDS` list for
both surfaces. It must not discover required IDs by scanning the inventory it is checking;
otherwise a feature that disappears entirely could also disappear from the discovered list
and falsely pass.

Planned executable targets:

- `scripts/check-valley-completeness.mjs` for the exact positive guard;
- `tests/valley-completeness-negative.test.ts` for mutation-based negative regression; and
- a hand-written machine-readable registry whose rows exactly mirror the IDs and targets in
  this document.

For every required surface and feature ID, the positive guard checks exact equality for:

1. one implementation registration and its exact owning path;
2. one resolvable documentation anchor;
3. every required English, Cantonese, bilingual, funny-level, School-mode, and emoji-off
   localization key;
4. one focused test file and exact test-case ID;
5. one built interaction record whose build identity matches the candidate;
6. one capture record and image hash for the same build and exact feature state; and
7. the row's explicit state, which must be `Complete` for release unless the fixed contract
   itself marks the row not applicable with the same rationale recorded here.

Paths, IDs, keys, anchors, build identities, and hashes are exact tokens. Descendant paths,
substring matches, renamed symbols, another surface's records, or a capture from a different
build do not satisfy them.

Negative mode works in a temporary copy and removes or disables exactly one asserted item at
a time: the feature row, implementation registration, documentation anchor, localization
key, focused test case, interaction record, capture record, or evidence hash. Every mutation
must make the guard fail with the exact surface, feature ID, and missing dimension. Restoring
the item must make the same case pass.

Additional fixed mutations must turn the guard red when:

- a counted Valley definition is duplicated, missing, lacks evidence, or moves any category
  below 500 crops, 250 trees/orchard plants/bushes/vines, 150 animal species, 400 factories,
  300 other buildings, 1,500 products, 1,200 recipes, 300 materials, or 400 functional
  outdoor objects;
- the named NPC count is anything other than exactly 240;
- any of the 700 structures lacks a reachable interior, real visible-door destination,
  functional station, operational restroom and hand-washing path, NPC behavior, save/reload
  persistence, or matching packaged evidence;
- a converter enables an unbundled adapter or implements an unlimited queue by retaining all
  files or bytes in memory;
- the Ollama store is curated rather than exhaustive, lacks fit evidence, treats its cart as
  payment, permits arbitrary shell execution, omits failed-launch rollback, accepts an
  unsupported attachment, or ends at unguided online documentation; or
- an authenticator secret, QR payload, password, code, private vocabulary file content,
  source path, or custom-logo source leaks into logs, history, exports, captures, prompts,
  analytics, telemetry, or a network request.

The guard is designed to fail until the planned implementations and evidence exist. This
documentation lane defines the design only; it does not add the script, registry, tests, or
evidence files.
